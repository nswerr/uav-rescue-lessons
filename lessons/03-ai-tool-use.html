AI 整合 ・ LESSON 03

讓 AI 呼叫找路工具

使用者想說的是「從第 4 列第 1 欄出發，到第 4 列第 8 欄，避開禁飛格」，而不是填表單。這篇說明怎麼讓語言模型聽懂這句話，卻把真正的計算交給第 02 篇的 BFS。

難度基礎
閱讀15 分鐘
先備第 02 篇

學習目標

  • 能說明為什麼找路要交給程式，而不是讓模型直接回答路徑。
  • 能寫出 find_path 工具的參數定義與回傳格式。
  • 能規劃缺少座標或 API 斷線時的備案。

一　誰負責什麼

語言模型很會理解人話，但不擅長保證每一步都算對：它可能說出「共 9 步」，實際卻穿過了禁飛格。所以我們採用工具使用（Tool Use）：模型只負責把指令轉成參數，計算由 Python 完成。

角色負責的事不做的事
語言模型從句子取出起點、目標座標；決定要不要呼叫工具；用自然語言說明結果自己算路徑或步數
Python 工具檢查座標範圍與禁飛格；執行 BFS；回傳路徑與步數解讀使用者的語氣或意圖
Gradio 介面收集輸入、讓使用者編輯禁飛格、依工具結果畫地圖修改計算結果

二　一次對話的流程

  1. 輸入任務一句話描述起點與待查點
  2. 模型擷取參數提出 find_path 工具呼叫
  3. Python 計算驗證輸入並執行 BFS
  4. 回覆與畫圖模型解說，介面依結果畫路線
畫面只相信工具結果

地圖上的路線一律由工具回傳的座標畫出，不從模型的文字裡解析。這樣就算模型說錯，畫面也不會錯。

三　定義 find_path 工具

工具定義告訴模型「有這個函式、需要哪些參數」。下面是支援工具呼叫的 API 常見的 JSON 結構（Groq 等相容 OpenAI 格式的服務都接受這種寫法）：

{
  "type": "function",
  "function": {
    "name": "find_path",
    "description": "在目前的搜救地圖上，用 BFS 找出起點到待查點的最短路徑",
    "parameters": {
      "type": "object",
      "properties": {
        "start": {"type": "array", "items": {"type": "integer"}, "description": "[列, 欄]，從 1 開始"},
        "goal":  {"type": "array", "items": {"type": "integer"}, "description": "[列, 欄]，從 1 開始"}
      },
      "required": ["start", "goal"]
    }
  }
}

注意禁飛格不是參數：工具每次都直接讀介面上目前的地圖，避免模型漏傳或亂改障礙資料。

四　統一的回傳格式

不管成功或失敗，工具都回傳同樣形狀的資料，讓模型和介面都好處理。

status其他欄位何時出現
okpath、steps找到路，例如範例地圖回傳 steps: 7
no_pathmessage起點和待查點被禁飛格完全隔開
invalid_inputmessage座標超出地圖，或起點／待查點本身是禁飛格

五　缺資料與斷線時的備案

指令缺少座標

例如使用者只說「幫我去待查點」。這時模型不應該猜座標，而是請使用者補上起點。可以在系統提示（system prompt）中寫明：「缺少起點或目標時，先詢問，不要呼叫工具」。

模型 API 暫時無法連線

介面另外保留起點、目標兩個輸入欄，直接呼叫同一個 Python 函式。展示時就算網路出問題，地圖與改道結果仍能照常示範。

不要讓模型繞過工具

若模型直接用文字回答路徑而沒有呼叫工具，介面應提示「未取得工具結果」，而不是把文字當成答案。

重點回顧

  • 模型負責理解與說明，Python 負責計算，畫面只採信工具回傳的座標。
  • find_path 只需要 start、goal，禁飛格由工具自己讀取。
  • 回傳一律帶 status：ok、no_path、invalid_input。
  • 缺座標就詢問；API 斷線就改用表單直接呼叫同一個函式。
